# 基于证据的主题与组件展示页

给定一个产品的 URL 或构建产物，产出一份独立的静态原型基线，提取可复用的主题、组件与版式约束，供后续项目原型使用。

**核心原则：**在来源证实之前，绝不断言某个颜色、组件、框架或业务领域是真实的。预览中的每一个决定都必须可追溯到产物、页面标记、运行时 DOM 或显式的主题配置。

## 何时使用

当用户希望以文档形式*看到*一个现有产品的视觉识别与 UI 组件时使用：

- "分析这个URL/产物，生成主题和组件展示页"
- "把这个站点的主题色和实际组件做成一个静态 HTML 原型"
- "make a component showcase from this site/artifact"

不要在用户想要构建新应用、从零重新设计，或为正在运行的产品截图时使用。

## 证据规则（先于其他一切阅读）

1. **禁止凭记忆使用颜色或组件。**不要复用来自本 skill、其他产品或历史运行中的调色板、类名词汇或示例内容，除非当前来源中出现了相同的值。
2. **禁止输出固定模板。**`references/showcase-skeleton.html` 只展示中性的页面结构与 CSS 约定。它不是可照抄的最终示例；其中的颜色、组件集合与内容均为占位符。
3. **证据质量排序：**
   - **DOM/计算样式证据**（最高）：渲染后的页面元素、类名、内联 `<style>`、计算得到的颜色与布局值。
   - **显式源码 token**：CSS 自定义属性（`:root`）、SCSS `:export`、框架主题对象（Material UI `palette`、Ant `theme` 等）。
   - **静态特征**：CSS 选择器、HTML 标记、JS 包字符串、框架/组件类名前缀。
   - **低置信度启发式**：颜色频次、`theme-color` meta、favicon 颜色。仅在标注为低置信度时使用，绝不能作为主调色板。
4. 任何没有真实证据支撑而构建的内容必须标记为 **fallback（兜底）**。在这些区块上使用 `data-evidence="fallback"`，并在可见标签中写明"模拟/未在产物中确认"。绝不能把兜底样式当作产品的真实样式呈现。
5. 输出保持为单个自包含的静态 HTML 文件。不引入框架、构建步骤或真实交互。

## 高保真参照门禁

当用户提供了、或明确授权了高保真参照 HTML、CSS、截图或已渲染路由时，将这些材料视为视觉实现的第二事实来源。

- **高保真参照：**检查其完整的 DOM 模式、样式表声明，以及（可用时的）渲染/计算样式。在契约中将其路径与目标产物一并记录。
- **不要**根据主题 token、对框架的熟悉度或类名去**合成**一个视觉上相似的控件。对每一个声称为高保真的组件，必须从获授权的参照中复制精确的 DOM 结构与 CSS 几何，包括嵌套插槽、控件元素、边框、内边距、圆角与状态选择器。
- CSS 前缀、source-map 字符串或静态选择器可以确立一个 `inferred`（推断）组件，但永远无法确立一个高保真组件。没有完整的 DOM 模式或计算样式捕获时，只在推断区呈现它，或直接省略。
- 如果参照是一份共享主题文档而非目标的运行时，应称其样式为**参照保真度**，而非目标运行时保真度。不要声称对目标路由达到像素级保真。
- 对于独立预览，将获授权参照中被页面实际使用的 CSS 内联进来。不要留下外部 CSS、字体、脚本或运行时 UI 库作为依赖。

## 原型契约

阅读 `references/contract-schema.md`。每个被提取的条目属于 `source`（DOM/计算样式或显式 token）、`inferred`（有 CSS/JS 支撑但未在运行时观测到）、`fallback`（为基线完整性所需）或 `chrome`（中性文档外壳）之一。推断组件要渲染在独立的区块中，并带可见的 `推断` 标签；绝不能称之为已观测。将契约嵌入 `script#theme-contract[type="application/json"]`，但不要渲染其 JSON。

## 系统组成推理

在渲染组件之前阅读 `references/system-composition.md`。从整个产物中识别应用外壳、页面模式、复合业务组件与基础原语；框架特征签名仅用于支持这一推断。围绕发现的组成关系图及其父子关系来构建展示页，而不是按组件库类别清单逐项核对。为全部四个层级给出覆盖度小结；若某层级无法确立，写明 `未找到证据`。

## 原型主题最低覆盖要求

预览是项目原型基线，而不是一份简略的分析报告。在证据支持的前提下，至少要展示完整的有状态组件清单：按钮各变体与禁用态；状态标签；输入/选择/日期控件；单选/复选/开关；校验；工具栏与标签页；筛选区域；带选择列/操作列的数据表；分页；卡片；警告/加载/空状态；对话框/抽屉/气泡浮层。这些控件必须依据目标系统的 token 与 CSS 几何重建，而不是采用框架默认样式。然后在路由/组件证据允许时，补充目标特有的复合组件，以及至少三个完整工作区（列表、详情/编辑、审批/流程）。这一最低要求与一份完整的"HTML 原型主题"页面相当；系统特有的覆盖面必须在其上进一步扩展。

## 工作流程

### 1. 检查输入

- **URL**：先抓取 HTML。读取 `<title>`、meta、已加载的 CSS/JS 资源。若页面是 JS 渲染的 SPA 且有可用的无头浏览器，渲染它并导出结果 DOM/计算样式。若渲染失败或被拦截，降级为仅源码分析，并在页脚说明。
- **dist / 静态目录**：定位编译后的 CSS（`*.css`、`theme-chalk`、Vite/Webpack 产物包）、HTML 模板与 JS chunk。优先处理声明了主题变量、`:export` token 或框架主题对象的文件。
- 若任何来源都无法触达，不要阻塞流程：告知用户预览将仅基于可用/已知值生成，并标注缺失的证据。

### 2. 识别产品与框架

- 产品名称与业务领域：从 `<title>`、页面标题、菜单项、标签与可见文案中推导。来源含糊时不要猜测领域。
- UI 框架/组件库：将 CSS 前缀、类名与 JS 字符串同 `references/framework-signatures.md` 比对。记录是哪一条特征、哪一个文件证明了匹配。

### 3. 提取主题

- 只收集当前来源中出现的值，按上述证据质量顺序取舍。
- 在来源有命名时，将颜色映射到语义角色（`primary`、`secondary`、`danger`、`pageBg`、`textLightColor` 等）。不要重命名或发明语义含义。
- 可发现时也记录版式约定：圆角、字体族、输入框高度、内边距、边框、阴影、页面背景。
- 若某个常见角色没有证据（例如找不到警告色），就省略它，或放在"未找到证据"之下展示，而不是自行挑选一个颜色。

### 4. 发现组件（结构优先）

**不要**从固定清单（Button、Dialog、Tree……）出发。先从 DOM/CSS/JS 中发现可复用块，再（可选地）映射到已知类别。使用同一组件库的两个产品会得出不同的组件清单与不同的内部版式；未知的产品控件同样属于展示页的内容。

完整遵循 `references/component-discovery.md`。摘要：

**4a. 聚类**

- 运行时 DOM：重复出现的同构子树、具有插槽形态的子结构（header/body/footer、list/item、label/control）、地标角色、浮层+面板结构。
- CSS：按共享根前缀分组选择器（BEM / `el-dialog__*` / 产品的 `foo-bar`）。一个前缀若有 3 条以上相关规则或 hover/选中状态，即为候选。
- JS：与某个 CSS 或 DOM 根节点相匹配的已注册/已导出符号名。
- SPA 首屏渲染不完整——仍然采纳仅出现在 CSS/JS 中的前缀。

**4b. 信号 ≥ 2 个时升级**（重复、插槽、专属 CSS、角色、浮层、JS 名称）。跳过工具类与一次性的页面外壳。

**4c. 命名**

- 命中组件库对照表 → 使用该类别名，同时保留本地的类名/符号名。
- 否则使用观测到的类名或 JS 名称。
- 否则使用结构标签（"浮层 + header/body/footer"、"嵌套缩进 + 展开箭头"）。绝不因为某个簇不在表里就丢弃它。

**4d. 捕获与重建**

为每个升级的块记录：根节点、插槽顺序/对齐、重复子项模板、token、状态、证据等级（`dom` / `css-prefix` / `js-name` / `structure-inferred`）。依据这份捕获来重建演示——而不是用现成的组件库样例或骨架中的占位控件。

**4e. 补抄与兜底**

- 从未出现过的库控件，只能以 `data-evidence="fallback"` 的方式加入。
- 示例文案取自页面/产物。若没有，使用 用户/任务/团队/数据/设置。绝不能默认设定一个业务领域。

### 5. 生成展示页

- 用 `references/showcase-skeleton.html` 的中性版式构建一个静态 HTML，将每个占位符替换为提取出的证据值。
- 存在获授权的高保真参照时，用其精确的 DOM 结构替换相关的中性组件标记，并内联其样式表规则。不要另造一套平行手写的组件体系。
- 调色板与组件区块必须携带溯源信息以便审查。可添加形如 `<!-- evidence: css:primary-main=#673AB7 -->` 的 HTML 注释，或使用 `data-evidence` 属性。
- 页面不得声称检测到未曾检测到的框架、组件或调色板。页脚需写明：来源 URL/路径、检测到的技术栈、主色/主要颜色，以及任何兜底/缺失证据。

### 6. 收尾前核对

- 展示的每个 source/inferred 级十六进制色值或渐变，都出现在已收集的证据中；显式标注为 `chrome` 的 token 豁免。
- 输出中不得残留来自以往示例的文字、颜色或组件名。
- HTML 能独立打开、渲染不依赖网络（旧模板中可选的 Element-UI 链接绝不能照抄过来）。
- 对每个高保真参照组件，将生成的 DOM 与完整 DOM 模式进行比对，核对其必需的 CSS 选择器与 token 值是否齐全。当可使用浏览器时，在相同视口下用计算样式验证有代表性的参照与预览，每个组件族至少抽查一个实例。
- 使用无侧栏的线性页面结构：摘要、主题/字体排印、已观测组件、推断组件、版式样例、可选的兜底项、局限说明。未被直接观测的组合要可见地标注 `原型组合推断`。
- 不提交凭据、不绕过访问控制、不遍历无关路由。若渲染不可用，在契约与页脚中记录"仅源码分析"这一限制。

## 输出

- 写入当前仓库根目录下的 `theme-preview-<sanitized-product>.html`，除非用户另行指定文件名。若文件已存在，追加 `-<YYYYMMDD-HHmmss>`；绝不静默覆盖。
- 页头副标题需点名真实产品与检测到的框架，例如"基于 <source> 分析 · React + Material-UI"。
- `lang` 跟随用户语言；含糊时默认 `zh-CN`。

## 常见错误

- 照抄 `references/showcase-skeleton.html`、旧的 IP-EMR 输出或任何记忆中的调色板作为最终产物。
- 产品是 Material UI、Ant Design 或自研样式时，却把预览做成 Element-UI 风格。
- 发明来源中不存在的语义色名（`mainColorDeep`）。
- 对所有产品套用固定业务文案（医疗/电商/后台）。
- 在 `:root` CSS 变量之外留下硬编码颜色。
- 只有框架特征或通用兜底支撑时，却声称组件存在。
- 从组件库类别表出发，只演示能对上号的行。
- 因为某个重复出现的 DOM/CSS 簇没有标准名称（筛选条、实体头部、甘特图行……）而丢弃它。
- 把发现的块重建为现成的库控件，而不是按其捕获的插槽/token 重建。
- 只分析第一个 URL 的抓取结果，忽略只出现在 CSS/JS chunk 中的前缀。

## 危险信号 —— 停下并重新核查证据

- "这个主题应该是 X"，却没有文件/DOM 匹配。
- 因为"看起来相似"就复用上一个产品的调色板。
- 把旧 `template.html` 的全部内容抄进新的输出。
- 把兜底演示标记为"已确认"。
